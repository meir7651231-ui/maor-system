# BUILD-ORDER · אכיפת-הרשאות בשכבת-הנתונים (Data-Layer Enforcement)

**תאריך:** 14.8.2026 · **סטטוס:** תכנון (הכרעת-בעלים: "לתכנן רי-ארכיטקצורה") · **מקור:** נחיל-עמוק #11 (disputed 1/2) + הכרעת-בעלים 13.8 (ג' — ייעוד פר-עובד) + 🔐 חסימת-ייצוא פר-עובד.

> מסמך **תכנון בלבד** — אין בו קוד. מגדיר את הבעיה, האילוץ, האפשרויות, ההמלצה, וסדר-בנייה מלועס לפאזות. **דורש הכרעות-בעלים** לפני יציאה-לפועל (מסומנות ⚖️).

## 1. הבעיה במשפט

היום כל **חבר-ארגון** מקבל `read+write` מלא ל-`orgs/{slug}/**` (firestore.rules). כל חסימות-הייצוא (#125/#127) והייעוד-פר-עובד (#124) הן **ברמת-הממשק בלבד** — עובדת טכנית יכולה לעקוף אותן דרך קונסולת-הדפדפן / Firestore SDK ולקרוא/לכתוב את **כל** נתוני-הארגון. אין אכיפה בשרת.

## 2. למה זה לא נסגר עם Rules (האילוץ הקשה)

המערכת היא **local-first · סנכרון-כל-ה-DB**:
- `pullAll` (`lib/cloud.ts`) עושה `getDocs` על **אוסף שלם** לכל ישות (21 אוספים) → כל חבר קורא את כל הקולקציה.
- `subscribeAll` — `onSnapshot` על אוספים שלמים.
- `pushDiff` דוחף את ה-diff של **כל ה-DB המקומי**; `fullDbDiff` (חיבור-ראשון/מיגרציה) דוחף הכל.

**מגבלת Firestore Security Rules:**
1. **קריאת-list אינה ניתנת-לסינון-לפי-שדה.** כלל-קריאה מאשר/דוחה **מסמך שלם** מול המבקש; אי-אפשר "החזר רק תרומות בייעוד V". שאילתת-אוסף = הכל-או-כלום.
2. **תרומות ממוזגות בתוך מסמך-התומך** (`Supporter.donations[]`) — ייעוד הוא שדה **בתוך** איבר-מערך, לא מסמך. Rules לא בוחנות איברי-מערך פר-הרשאה.
3. **הגבלת-כתיבה פר-חבר שוברת סנכרון:** חבר עם מודול-כבוי שידחוף `fullDbDiff` (שכולל אוסף שקיבל מהענן) → הכתיבה תידחה → הסנכרון-הראשוני נשבר.

⇒ **המסקנה:** אכיפה-אמיתית דורשת שינוי בשכבת-הנתונים/הסנכרון עצמה, לא רק Rules. זו הסיבה שהממצא חזר `disputed` — ספקן אחד זיהה שזו התנהגות-מודל, לא באג-נקודתי.

## 3. שלושה מסלולים (עם trade-offs מול האינווריאנטים)

האינווריאנט-העליון של הפרויקט: **local-first · אפס-אובדן-יכולת · הלקוח-הקיים לא זז (cloudRoot ביט-זהה)**. כל מסלול נמדד מולם.

### מסלול A — שער-סנכרון מתווך-שרת (Cloud Functions gateway)
- הלקוח לא נוגע ב-Firestore ישירות; קורא/כותב דרך פונקציה (`syncGateway`) שמפעילה `effectiveConfigFor` בשרת (Admin SDK) ומחזירה **רק** את המותר לחבר (מסונן-ייעוד), ומקבלת כתיבות רק לתחום-המורשה.
- Rules: `orgs/{slug}/** → allow read,write: if false` (רק Admin SDK).
- 🟢 אכיפה-אמיתית מלאה (קריאה+כתיבה+ייצוא — הכל עובר שרת). 🔴 **שובר offline-first** (כל סנכרון דורש רשת), latency, עלות-פונקציות, ותלות-Blaze. 🔴 שכתוב-מלא של שכבת-הסנכרון.
- מתאים אם מוותרים על offline-first לחברים-מוגבלים (המנהל/בעלים יכולים להישאר ישירים).

### מסלול B — חלוקת-נתונים פר-ייעוד (subcollections) 🟢 מומלץ
- תרומות יוצאות ממסמך-התומך ל-subcollection פר-ייעוד: `orgs/{slug}/donations/{purpose}/items/{id}` (או doc-per-donation עם שדה-purpose ב-path-segment). מסמך-התומך = נתוני-בסיס משותפים.
- Rules: `allow read: if memberDesignations(slug).hasAny([purpose]) || isManager` — **פר-subcollection, לפי memberConfigs**. זה **כן** מתבטא ב-Rules (המסמך-בכללותו שייך לייעוד).
- 🟢 **שומר offline-first** (הלקוח נשאר ישיר-ל-Firestore). 🟢 אכיפת-קריאה אמיתית פר-ייעוד. 🟡 קבלות/צבירות חוצות-subcollections. 🔴 שינוי-מודל-נתונים גדול + מיגרציה + שכתוב מנוע-הסנכרון (cloud-diff) לטפל ב-subcollections. 🔴 ייעודים דינמיים (ייעוד-חדש = path-חדש).
- **חסימת-ייצוא (core.export)** עדיין UI-level גם כאן (Rules לא מבחינות read-לתצוגה מ-read-לייצוא) — אך אם החבר לא **יכול לקרוא** את הייעוד האסור, גם לא יוכל לייצא אותו ⇒ הייצוא נאכף **בעקיפין** דרך אכיפת-הקריאה.

### מסלול C — projection-per-member שמתוחזק ע"י function
- פונקציה מתחזקת עותק-מסונן פר-חבר. 🔴 מורכב, סיכון-בייתנות (stale), עלות-אחסון כפול. **לא מומלץ.**

### המלצה
**מסלול B** — הוא היחיד ששומר על ה-local-first (ערך-ליבה) ומספק אכיפת-קריאה אמיתית. חסימת-הייצוא נאכפת בעקיפין (אין-קריאה⇒אין-ייצוא). מסלול A רק אם הבעלים מוכן לוותר על offline לחברים-מוגבלים.

⚖️ **הכרעת-בעלים נדרשת:** B (partition, שומר-offline) מול A (gateway, אכיפה-מלאה אך online-only).

## 4. סדר-בנייה מלועס — מסלול B (partition פר-ייעוד)

> כל פאזה = commit נפרד + ratchet. **אף פאזה לא נוגעת בלקוח-השורש** (`cloudRoot` — ביט-זהה, ratchet-הגנה). המיגרציה חד-כיוונית ובלתי-הרסת (העתקה, לא מחיקה, עד אימות).

**פאזה 0 — quick-win שאינו-תלוי (ניתן להפריד ל-Rules v4 מיידי):**
- `platformLeads`: הוסף הגבלת-גודל/שדות מחמירה + rate (וקטור-spam ציבורי, נחיל #). זה עצמאי ואפשר לפרסם מיד בלי המסלול הגדול.

**פאזה 1 — מודל-הנתונים (טהור, בלי חיווט):**
- הגדר `DonationRef` = doc-per-donation ב-`orgs/{slug}/donations/{id}` עם שדה `purpose` (ריק='משותף'). מסמך-התומך שומר נתוני-בסיס בלבד (שם/טלפון/ת"ז/ציון) — **בלי** `donations[]` בענן.
- ⚠️ **קבלות מס (rid) חוצות-ייעוד** — receiptSeq/donationSeq נשארים ב-meta (לא ב-subcollection). אימות: רציפות-R-/D- לא נשברת.
- ratchet: המרה טהורה supporter↔{base, donationRefs[]} דו-כיוונית, זהות-מלאה.

**פאזה 2 — מנוע-הסנכרון (cloud-diff/cloud):**
- הרחב `ENTITY_COLLECTIONS`/`cloud-diff` לטפל ב-donations כאוסף-עצמאי (doc-per-donation) במקום מקונן-בתומך.
- `pullAll`/`subscribeAll`: קריאת donations מסוננת לפי `allowedDesignations` (query `where('purpose','in',allowed)` לחבר-מוגבל; ללא-סינון למנהל).
- ⚠️ **תאימות-לאחור:** מכשיר-ישן שדוחף `Supporter.donations[]` — פונקציית-מיגרציה חד-פעמית (פאזה 4) + נתיב-קריאה שמאחד.
- ratchet: סנכרון donations-כאוסף שומר על אינווריאנט-המונים (מהאשכול-ענן שזה-עתה).

**פאזה 3 — Rules v4 (אכיפה):**
- `match /orgs/{slug}/donations/{id}`: `allow read: if isManager(slug) || memberSeesPurpose(slug, resource.data.purpose)`; `memberSeesPurpose` קורא `memberConfigs[email].designations` דרך `get()`.
- שאר-האוספים: כהיום (חבר). ⚠️ ה-query בלקוח **חייב** להיות מסונן (Firestore דוחה list לא-מסונן שלא עובר Rules) — נאכף בפאזה 2.
- ratchet: בדיקת-Rules (emulator) — חבר-מוגבל נדחה על donation בייעוד-אסור, מותר על מותר/משותף.

**פאזה 4 — מיגרציה חיה (חלון-בעלים):**
- העתקת `Supporter.donations[]` → אוסף-donations בענן, פר-ארגון-מוצפן/לא. חד-כיוונית, בלתי-הרסת (הישן נשאר עד אימות). דומה למיגרציית-הצפנת-הענן (Runbook נפרד).

**פאזה 5 — UI + ניקוי:**
- ה-UI כבר מסנן (visibleSupportersForDesignations) — כעת המקור כבר-מסונן מהשרת, ה-UI הופך שכבה-שנייה (defense-in-depth). ניקוי `donations[]` המקונן מהמודל-המקומי אחרי אימות-מלא.

## 5. סיכונים / שאלות-פתוחות ⚖️
1. **offline לחבר-מוגבל:** query `where purpose in allowed` עובד offline מול המטמון-המקומי? (Firestore persistentCache — כן, אך רק על מה שכבר-נמשך). לבדוק.
2. **קבלה חוצת-ייעוד:** תורם עם תרומות בכמה ייעודים — הקבלה השנתית/המס. הוכרע 9.8 (קבלות-בלבד); לוודא שהפיצול לא שובר רציפות-rid.
3. **ייעוד-חדש דינמי:** memberConfigs מפנה לייעוד שטרם קיים — Rules `in []` = ריק ⇒ רואה רק משותף. תקין.
4. **עלות/מורכבות מול התועלת:** האם מודל-האמון (עובדות=צוות-אמון) מצדיק פרויקט-שבועות? החלטת-בעלים.

## 6. מה לא משתנה (אינווריאנטים נשמרים)
- הלקוח-השורש (`default`/`cloudRoot`) — **ביט-זהה**, פטור מהמסלול (ratchet-הגנה כמו CLOUD2).
- אפס-אובדן-יכולת: כל הזרימות הקיימות נשמרות; ה-UI-filter נשאר כשכבה-שנייה.
- מונים-רק-עולים (אינווריאנט-הענן) — receiptSeq/donationSeq נשארים ב-meta, לא בפיצול.

---

**החלטה נדרשת לפני פאזה 1:** ⚖️ מסלול B (partition, שומר-offline · מומלץ) מול A (gateway, אכיפה-מלאה online-only). ומיד-בר-ביצוע ללא-תלות: פאזה-0 (platformLeads spam) כ-Rules v4 קצר.
